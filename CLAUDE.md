# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working
with code in this repository.

## Project

`bixverse.gpu` is an R package providing GPU-accelerated algorithms (kNN
search, k-means, PCA, Harmony, UMAP, tSNE, parametric UMAP, SCENIC,
SEACells meta cells, Scrublet doublet detection, correlations) that plug
into the `bixverse` / `manifoldsR` ecosystem. The heavy lifting is Rust,
exposed to R via `extendr`. GPU code runs on WGPU via `cubecl` / `burn`,
so it is portable across vendors (no CUDA required).

## Common commands

Rextendr-based workflow. Run from an R session at the repo root:

``` r

devtools::load_all()          # build the Rust static lib + load the package
devtools::document()          # since rextendr 0.5.0 this also compiles Rust and regenerates R/extendr-wrappers.R from #[extendr] fns; use this after editing Rust
rextendr::clean()             # nuke cargo build artifacts (e.g. after Cargo.toml changes)
tinytest::test_package("bixverse.gpu")   # run the full test suite
tinytest::run_test_file("inst/tinytest/test_gpu_kmeans.R")  # run one test file
```

Rust builds live under `src/rust/target/` and are always release
(`opt-level = 3`), which is CRAN policy. `DEBUG=1` is ignored by
`tools/config.R`; do not add a debug path.

During development set `DEV_BUILD=true`. It keeps `src/rust/target/` and
the shared cargo registry warm between installs and drops LTO, which
cuts a `document()` cycle from minutes to seconds. Still a release
build, so do not benchmark or submit from one. It deliberately does not
engage on a vendored build, where `CARGO_HOME` has to stay local for
`vendor-config.toml`.

R CMD check runs in CI (`.github/workflows/R-cmd-check.yml`) on macOS
and Ubuntu. Linux CI installs `libvulkan1` / `mesa-vulkan-drivers` and
sets `WGPU_BACKEND=vulkan`.

Formatting: R code uses `air` (`air.toml` present). Rust is stock
`cargo fmt`.

## Architecture

The package is a thin R shim over a Rust crate. Three layers, top-down:

1.  **R user API** (`R/*.R`): friendly, validated wrappers. `sc_gpu.R`
    (single-cell workflows, S7 generics dispatching on `SingleCells` /
    `SingleCellsMultiModal` from `bixverse`), `scenic_gpu.R` (SCENIC GRN
    inference, dispatching on `SingleCells` / `MetaCells`),
    `seacells_gpu.R` (SEACells meta cells, dispatching on `SingleCells`
    / `SingleCellsSubset`), `scrublet_gpu.R` (Scrublet doublet
    detection, dispatching on `SingleCells`), `umap_gpu.R`,
    `tsne_gpu.R`, `parametric_umap.R`, `ml_gpu.R` (k-means), `nn_gpu.R`
    (kNN graphs), `utils.R` (`parse_verbosity`). Argument checks use
    `checkmate` plus local `checkmate_extensions.R`, where each
    `checkXParams()` predicate is wrapped into an `assertXParams()` via
    [`checkmate::makeAssertionFunction`](https://mllg.github.io/checkmate/reference/makeAssertion.html)
    (`assertNnParamsGpu`, `assertUmapParamsGpu`, `assertTsneParamsGpu`,
    and so on). Parameter builders live in `param_wrappers.R`
    (`params_sc_cagra`, `params_sc_ivf`, `params_nn_gpu`,
    `params_umap_gpu`, `params_tsne_gpu`, `params_kmeans_gpu`,
    `params_parametric_umap`, `params_sc_harmony_v2_gpu`): each returns
    a plain named list that the corresponding assert function then
    validates before it crosses into Rust. SCENIC and SEACells have no
    local builder: they reuse
    [`bixverse::params_scenic()`](https://gregorlueg.github.io/bixverse/reference/params_scenic.html)
    / `bixverse:::assertScenicParams()` and
    [`bixverse::params_sc_seacells()`](https://gregorlueg.github.io/bixverse/reference/params_sc_seacells.html)
    / `bixverse:::assertScSeacells()` respectively.
2.  **extendr bridge** (`R/extendr-wrappers.R`): GENERATED by
    [`rextendr::document()`](https://extendr.github.io/rextendr/reference/document.html)
    from `#[extendr]` attributes in Rust; never edit by hand. Any change
    to a Rust-exposed function signature or doc comment requires
    re-running `document()`.
3.  **Rust crate** (`src/rust/`, package name `bixverse_gpu`).
    `src/lib.rs` holds the top-level `extendr_module!` registration, the
    precision helpers (`parse_precision`, `auto_precision`,
    `SAMPLE_THRESHOLD_HIGH_PRECISION`) and the `PUmapModel`
    backend-agnostic wrapper. It also holds most `#[extendr]` entry
    points, but not all: `pca_gpu.rs`, `harmony_gpu.rs`,
    `scenic_gpu.rs`, `scrublet_gpu.rs` and `seacells_gpu.rs` each carry
    their own, registered through `use <mod>;` lines inside
    `extendr_module!` rather than `fn` lines. Subdirectories:
    - `embeddings/`: `umap_gpu.rs`, `tsne_gpu.rs`, `parametric_umap.rs`
      (neural-net UMAP with GPU and CPU backends), `utils.rs` (R list to
      Rust parameter structs).
    - `single_cell/`: `knn_gpu.rs` (CAGRA / IVF / exhaustive),
      `pca_gpu.rs` (sparse randomised SVD), `harmony_gpu.rs`,
      `scenic_gpu.rs` (in-memory, streaming and MetaCells GRN drivers),
      `scrublet_gpu.rs`, `seacells_gpu.rs`, `sc_utils.rs` (shared
      cell-mapping and kNN conversion helpers; only `seacells_gpu.rs`
      consumes them so far).
    - `ml/clustering.rs`: k-means.
    - `utils.rs`: R to Rust matrix converters (`r_matrix_to_faer_fp32`,
      `faer_to_r_matrix`, `nearest_neighbours_to_rust`).

Backends: - `GpuBackend = Autodiff<Wgpu>`: the WGPU/cubecl path for all
“GPU” algorithms. - `CpuBackend = Autodiff<Flex<f32>>`: used by
parametric UMAP on the CPU path. `flex` replaced the old `ndarray`
backend for parametric UMAP.

Precision policy: UMAP/tSNE dispatch fp32 vs fp64 through
`parse_precision`, which honours the user’s `use_high_precision` arg or
falls back to `auto_precision` (fp64 above
`SAMPLE_THRESHOLD_HIGH_PRECISION = 100_000` samples). tSNE is called out
as precision-sensitive.

For the sibling Rust crates that own the actual algorithms, see the next
section.

## External Rust crates

Three sibling crates (same maintainer) hold most of the real work.
`bixverse.gpu` is largely a thin R interface into them. Knowing which
crate owns what matters when hunting a bug or extending an algorithm;
most GPU kernels do not live in this repo.

- **`ann-search-rs`**: approximate nearest-neighbour crate. Owns CAGRA /
  IVF / exhaustive kNN plus shared SIMD and GPU-tensor infrastructure
  that the other sibling crates reuse. Many of the GPU primitives
  dispatched from here originate there, including the GPU k-means
  (`ann_search_rs::gpu::k_means_gpu`), which used to live in
  `bixverse-rs`. (feature: `gpu`)
- **`bixverse-rs`**: Rust engine behind the whole `bixverse` ecosystem.
  This package consumes its GPU-accelerated pieces (linalg, PCA,
  Harmony, correlations, SCENIC, SEACells); the main non-GPU R-facing
  interface lives in the separate `bixverse` R package. (features:
  `gpu`, `single-cell`) It no longer owns the GPU k-means kernels, only
  the R-list parsing for them, via the `KMeansGpuParamsFromR` extension
  trait in `bixverse_rs::gpu::gpu_r_wrappers`.
- **`manifolds-rs`**: manifold-learning crate. UMAP, tSNE, diffusion
  maps, PaCMAP, PHATE. Depends on `ann-search-rs` for kNN. GPU coverage
  is expanding: kNN searches are already GPU, and the UMAP optimiser now
  has a GPU path too. (features: `parametric`, `gpu`, plus `fft_tsne`
  off-Windows, see the h5 toolchain issue in the README)

During development `src/rust/Cargo.toml` wires two of these to local
checkouts so you track their HEAD. `bixverse-rs` is a plain `path`
dependency, nothing else in the graph depends on it. `ann-search-rs`
cannot be: this crate, `bixverse-rs` and `manifolds-rs` all depend on
it, and a `path` dep would resolve to a second copy whose types no
longer match across the boundary. It goes through `[patch.crates-io]`
instead, which unifies the whole graph. Note that `bixverse-rs` carries
the same patch block, but patches only apply from the top-level
manifest, so it has to be repeated here. Both the `path` dep and the
patch block have to go before merging, otherwise CI cannot resolve them
and the vendored offline build path breaks.

## Conventions

- kNN indices returned to R are **1-indexed**. Rust returns 0-based and
  R adds 1 in `nn_gpu.R::generate_knn_graph`. Matrices returned to Rust
  are always cells x features / samples x features (row-major from R’s
  perspective).
- Verbosity everywhere: `0L` silent, `1L` normal, `2L` detailed. R-side
  accepts a boolean or `0/1/2`; funnels through
  [`parse_verbosity()`](https://gregorlueg.github.io/bixverse.gpu/reference/parse_verbosity.md)
  before crossing into Rust.
- S3 classes: `KMeansClusterGPU` (in `R/classes.R`) implements
  [`manifoldsR::membership`](https://gregorlueg.github.io/manifoldsR/reference/membership.html)
  / `get_centroids`. `ParametricUmapModel` has `print` and `predict`
  methods and can be serialised via `save_parametric_umap` /
  `load_parametric_umap` (bytes are tagged 0=GPU, 1=CPU by
  `rs_serialise_parametric_umap`).
- `.onLoad` in `R/zzz.R` calls
  [`S7::methods_register()`](https://rconsortium.github.io/S7/reference/methods_register.html).
  Do not remove it, the single-cell generics need it.
- Package is `lifecycle: experimental`, which covers the whole R-facing
  surface. Do not put `r lifecycle::badge("experimental")` in
  hand-written roxygen; the badge only appears on the `rs_*` wrappers,
  where it comes from the Rust `///` doc comments.

## Writing style

Applies to every surface where prose lands in front of a reader:
vignettes (`.qmd`), README, roxygen `@description` / `@details`, code
comments, commit messages, PR titles and descriptions.

Hard rules:

- No em-dashes, neither the ASCII nor the Unicode variant. Reads as
  AI-generated. Use commas, colons, semicolons, or full stops.
- British English. `normalise`, `randomised`, `centred`, `favour`,
  `analyse`, `colour`.
- No corporate filler: “leverages”, “utilises”, “seamlessly”,
  “cutting-edge”, “robust”, “state-of-the-art”, “empowers”, “enables”,
  “unlocks”, “delve into”.
- No hedge stacks (“may sometimes potentially”), no filler transitions
  (“Furthermore”, “Moreover”, “It is worth noting that”), no
  throat-clearing intros (“In this section we will walk through”).
- No trailing paragraphs that recap what the section just showed. The
  exception is a conclusion that adds something forward-looking
  (roadmap, caveats, what to try next).

Positive patterns:

- Short sentences. Active voice. Contractions are fine and usually
  better.
- Concrete over abstract, with numbers where possible. “25k points
  across 25 clusters in 32D” beats “a moderately sized clustered
  dataset”.
- Admit weaknesses directly. “On Apple Silicon the GPU rarely blows the
  CPU out of the water” beats hedging around it.
- Brief, specific editorialising is welcome (“gets painful fast”, “watch
  this space”). Once or twice per vignette, not per section.
- Keep `@param` / `@returns` roxygen bullets terse and structured. The
  style rules above are for prose blocks.

Older files may still contain em-dashes from before this rule. Do not go
on a retroactive rewriting spree, fix them when you touch the
surrounding prose anyway.

## Notes and non-obvious things

- The `document` binary in `src/rust/document.rs` is invoked by
  `Makevars` after the lib build to regenerate wrappers during install.
  That’s why `document.rs` sits alongside `Cargo.toml` and has its own
  `[[bin]]` entry.
- `configure` / `configure.win` plus `tools/config.R` and `tools/msrv.R`
  implement CRAN-friendly Rust detection and the vendored-crate offline
  build path (`src/rust/vendor.tar.xz`, generated at release time).
  Don’t hand-edit `src/Makevars`, it is generated from
  `src/Makevars.in`.
- `bixverse`, `bixverse.plots`, `manifoldsR` are `Remotes:`. Assume they
  are installed from GitHub in dev environments.
